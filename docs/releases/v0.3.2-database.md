# v0.3.2 database migration and rollback

This release adds the persistent same-day challenge ledger, its user/id index, and `focus_klines.challenge_policy_json`. All changes are additive. Startup creates the challenge table and index; the focus K-line schema helper adds the cache column. Existing focus sessions and settled candles remain the source of truth, and challenge decisions are stored as separate timestamped rows.

Before activation, the release validator makes a consistent SQLite backup of the current database while the service remains online, applies the candidate schema to that temporary clone, and verifies `quick_check`, `foreign_key_check`, the expected table/index/column, and unchanged row counts and hashes for every pre-existing table. The live database stays read-only during this rehearsal.

Activation takes an online backup, stops the service, then takes a second maintenance backup. With the service stopped, it applies the additive schema and compares every pre-existing table against the maintenance backup before switching the release symlink. The candidate starts only after those checks pass. Post-activation verification checks the expected schema, database integrity, service health, and public route status.

If activation fails, rollback restores the previous code symlink and restarts the service. It leaves the additive table and column in place because the previous release ignores them; it does not overwrite the live database with a pre-activation backup, which could discard writes made after service restart. Both backups are retained for recovery.
